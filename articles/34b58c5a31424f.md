# 第 1 章 はじめに
- **アンチパターン**: 避けるべき書き方
- **コンポーネント**: 再利用可能なソフトウェア要素
- 4 種類の型 (最初の 3 つは**参照型**とも)
  - **インターフェース** (**アノテーション**を含む)
  - **クラス** (enum を含む)
  - **配列**
  - **基本データ** (primitive)
- **オブジェクト**: クラスのインスタンスと配列
  - **メンバー**は**フィールド**，**メソッド**，**メンバークラス**，**メンバーインターフェース**からなる
  - **シグネチャ**はメソッド名，仮パラメータの方から構成される
- **サブクラス化**=**継承**
  - インタフェースを**実装** (**拡張**) すると呼ぶ
  - **パッケージプライベート**=**パッケージアクセス**
- **(公開) API**: クラス，インタフェース，コンストラクタ，メンバー，シリアライズ形式 (まとめて**API 要素**) を指し，これらによりプログラマ(**ユーザ**)はアクセスする
  - **クライアント**: ある API を使った実装を持つクラス
- **モジュールシステム**: ライブラリがこれを使っていれば，そのライブラリの公開 API はモジュール宣言で公開するとされたパッケージの公開 API の集合となる
# 第 2 章 オブジェクトの生成と消滅
## 項目 1 コンストラクタの代わりに static ファクトリメソッドを検討する
- static ファクトリメソッド: クラスのインスタンスを返す単なる static のメソッド
- (オート) ボクシング: プリミティブ型からラッパークラスへの変換
  - ボクシングされた基本データクラスも持つ

### 例
確率的素数の BigInteger を返すとき
- NG (コンストラクタ): `BigInteger(int, int, Random)`
- OK (static ファクトリメソッド): `BigInteger.probablePrime(int, Random)`

### 長所
1. **分かりやすい名前をつけることができる**
   - コンストラクタは名前が 1 つ(クラス名)に限定され，引数の違いでしか区別できない
2. **呼び出しごとに新たなオブジェクトを生成する必要がなく，同じオブジェクトを使いまわせる**
   - どの時点でもどのようなインスタンスが存在するかを厳密に制御 (インスタンス制御) することができる
     - クラスをシングルトン・インスタンス化不可能にできる
     - 不変な値クラスが 2 つの同じインスタンスを存在させないようにできる
3. **メソッドの戻り値の型そのものではなく，そのサブタイプのオブジェクトを返せる**
   - API がクラスを public にせずにそのオブジェクトを返せる(**インターフェースに基づくフレームワーク**に向いている)
   - 例: java.util.Collections の static なファクトリメソッド`emptyList()`
     - 内部クラス`EmptyList`のインスタンスを返すため外部から隠蔽でき，戻り値の型は`List`インターフェース
     - これにより，以下のように API が簡潔になる
       - 実装者にとっては、`EmptyList`の使い方（API）を利用者に説明する必要がない
       - 利用者にとっては、`EmptyList`の存在や使い方（API）を意識する必要が無く，`List`インターフェースの使い方だけ知っておけばよい
4. **返却するサブタイプのオブジェクトは，入力パラメータの値に応じて呼び出しごとに切り替えることができる**
5. **返却するオブジェクトのクラスは，その static ファクトリメソッドの実装時点で存在していなくても実行時に決まればよい**
   - 例: JDBC (**サービスプロバイダフレームワーク**の基盤)
     - サービスプロバイダフレームワークは以下からなる
	     - 実装を表す**サービスインタフェース**
	     - プロバイダが実装を登録するために使う**プロバイダ登録 API**
	     - クライアントがサービスのインスタンスを得るために使う**サービスアクセス API**
	     - サービスインタフェースのインスタンスを生成するファクトリオブジェクトの**サービスプロバイダインタフェース** (オプション)
### 短所
1. **利用者が戻り値の型のサブクラスを作れない**
   - `emptyList()`で返される EmptyList は private なクラスなのでこれのサブクラスを作れない
2. **利用者が static ファクトリメソッドを見つけるのが難しい**
   以下のように一般的な命名パターンがある

| 命名パターン           | 例                                                            | 意味合い                                                               |
| ---------------------- | ------------------------------------------------------------- | ---------------------------------------------------------------------- |
| from                   | `Date d = Date.from(instant);`                                | その型を持つ対応するインスタンスを返す**型変換メソッド**               |
| of                     | `Set<Rank> faceCards = EnumSet.of(JACK, QUEEN, KING);`        | それらを含んだその型のインスタンスを返す**集約メソッド**               |
| valueOf                | `BigInteger prime = BigInteger.valueOf(Integer.MAX_VALUE);`   | from, of と同じ意味で使われる                                          |
| instance / getInstance | `StackWalker luke = StackWalker.getInstance(options);`        | パラメータに応じたインスタンスを返す                                   |
| create / newInstance   | `Object newArray = Array.newInstance(classObject, arrayLen);` | 呼び出しごとに新たなインスタンスを返す                                 |
| get*Type*              | `FileStore fs = Files.getFileStore(path);`                    | 自身のクラスとは異なるクラスを返す                                     |
| new*Type*              | `BufferedReader br = Files.newBufferedReader(path);`          | 呼び出しごとに，自身のクラスとは異なるクラスの新たなインスタンスを返す |
| _Type_                 | `List<Complaint> litany = Collections.list(legacyLitany);`    | get*Type*, new*Type*の短縮版                                           |

## 項目 2 多くのコンストラクタパラメータに直面したときにはビルダーを検討する

## テレスコーピング・パターン: NG

必須パラメータだけを受け取るコンストラクタを 1 つ提供し，単一のオプションパラメータを受け取る別のコンストラクタを提供し，2 つのオプションパラメータを受け取る 3 つ目のコンストラクタを提供し，というように続けて，すべてのオプションパラメータを受け取るコンストラクタで終わるパターン

- 利用者にとってどうでも良いパラメータであっても設定を強制させてしまう
- 利用者が何番目のパラメータが何かを気にする必要がある
- コードの読み手にとって各パラメータの意味を理解しづらい
- 型さえ合っていればコンパイルエラーにはならないため，同じ型のパラメータを誤った順番で指定しても間違いに気づけない

```Java
public class NutritionFacts {
    // フィールド定義は省略
    public NutritionFacts(int servingSize, int servings) {
        this(servingSize, servings, 0);
    }
	public NutritionFacts(int servingSize, int servings, int calories) {
        this(servingSize, servings, calories, 0);
    }
	// 上記のような流れが延々と続いていく・・・
	public NutritionFacts(int servingSize, int servings, int calories, int fat,
		int sodium, int carbohydrate) {
		this.servingSize = servingSize;  // 必須
		this.servings = servings;  // 必須
		this.calories = calories;  // オプション
		this.fat = fat;  // オプション
		this.sodium = sodium;  // オプション
		this.carbohydrate = carbohydrate;  // オプション
	}
}
```

## JavaBeans パターン: NG

オブジェクトを生成するためにパラメータなしのコンストラクタを呼び出し，それから必要とされる各パラメータと関心のあるオプションパラメータを設定するためにセッターメソッドを呼び出すパターン

- インスタンス化した後にパラメータ間で不整合が起こるかもしれない
	- 本来はインスタンス化する前に不整合を検知すべき
- setter から内部の状態を変更できるのでクラスを不変にできない

```Java
public class NutritionFacts {
    // フィールド定義は省略
    public NutritionFats() {}
    public void setServingSize(int val) { //略 }
    public void setServings(int val) { //略 }
    public void setCalories(int val) { //略 }
    // まだまだsetterが続く・・・
}
```

## Builder パターン

望むオブジェクトを直接生成する代わりに，クライアントは必須パラメータをすべて持つコンストラクタ(static ファクトリメソッド)を呼び出して**ビルダーオブジェクト**を得て，クライアントが関心のあるオプションパラメータを個別に設定するためにビルダーオブジェクトに対してセッターのようなメソッドを呼び出し，最後に不変なオブジェクトを生成するためにパラメータを持たない`build()`メソッドを呼び出すパターン．
### 長所
- 実装しやすい
- 読みやすい
  - 名前つきオプションパラメータを模倣している
- `build()`でインスタンス化する前にパラメータ間の不整合を検知できる
	- 不整合がここで検知されず，遠い場所で不整合を起因とするエラーが起きてしまうと，原因の特定が困難になってしまう
- クラスが階層構造になっている場合でもこのパターンを適用できる
	  - 抽象クラスの Builder は**再帰的な型パラメータ**をもつ**ジェネリック型**となる (**疑似自分型イディオム**)
	  - 具象クラスの`build()`メソッドはその具象クラスを返す (**共変戻り値型付け**)
- API が柔軟になる
	- 1 つの Builderを使い回し`build()`内でシリアル番号を採番することで，一意なオブジェクトを複製できる
### 短所
- Builder をインスタンス化する必要があり，性能要件がシビアな状況では気にする必要 (実務上はは稀)
- テレスコーピングパターンより利用者のコードが長くなってしまう
	- パラメータの数が多い時に向いているが，パラメータの数は保守していくとどんどん増えることがある

```Java
public class NutritionFacts {
    // フィールド定義
	public static class Builder {
	    // フィールド定義
		public Builder(int servingSize, int servings) {  // 必須
			this.servingSize = servingSize;
			this.servings = servings;
		}
		public Builder calories(int val) {
			calories = val;
			return this;
		}
		// 各オプションパラメータについて同様
		public NutritionFacts build() {
			return new NutritionFacts(this);
		}
	}

	private NutritionFacts(Builder builder) {
		servingSize = builder.servingSize;
		servings = builder.servings;
		calories = builder.calories;
		fat = builder.fat;
		sodium = builder.sodium;
		carbohydrate = builder.carbohydrate;
	}
```

```Java
// 利用者側のコード
NutritionFacts cocaCola = new NutritionFacts.Builder(240, 8).
    calories(100).sodium(35).carbohydrate(27).build();
```

## 項目 3 private のコンストラクタか enum 型でシングルトン特性を強制する

クラスをシングルトンにすることでクライアントのテストを困難にする

シングルトン(厳密に 1 度しかインスタンスが作成されないクラス)を実現する方法は以下

1. enum 型でシングルトンを実装する(多くの場合これが最適)
2. private コンストラクタでインスタンスを 1 つ作り，public なフィールドに設定して公開する or static ファクトリメソッドで返却する

### enum 型でシングルトンを実装

```Java
public enum Elvis {
	INSTANCE;
	public void someMethod() { ... }
}
```

#### 利点

- private コンストラクタの場合では，利用者がリフレクションによって内部の private コンストラクタを呼び出せてしまうため，これを防ぐためのチェック処理を書かなければいけない
- シングルトンのクラスをシリアライズできるようにしたい場合，デシリアライズの度にインスタンスが生成されてしまう恐れがあるため，これを防ぐための処理を書かなければいけない

### private コンストラクタを使う 2 つの方法

#### 長所

こういった長所を得たいケースは限られるため，結局は多くの場合に enum が最適

- public なフィールドに設定して公開する
  - シングルトンであることが API から明確に理解できる
  - 単純
- static ファクトリメソッドで返却する
  - シングルトンにすべきかどうかを後から変更できる
  - ジェネリックのシングルトンファクトリにできる
  - メソッド参照を使える

## 項目 4 private のコンストラクタでインスタンス化不可能を強制する

ユーティリティクラス(static なメソッドと static なフィールドだけで構成されるクラス)は本来インスタンス化して使うべきではないが，コンストラクタが使えてしまうと誤ってインスタンス化されてしまう恐れがあるため，以下のように private なコンストラクタを実装する

```java
public class UtilityClass {
    // インスタンス化できないようにデフォルトコンストラクタを抑制する(とコメントで書いておく)
    private UtilityClass() {
        throw new AssertionError();
    }
}
```

## 項目 5 資源を直接結びつけるよりも依存性注入を選ぶ

例: 辞書に依存するスペルチェッカー

### NG(ユーティリティクラスとして実装)

```java
public class SpellChecker{
    // スペクチェックに使う辞書
    private static final Lexicon dictionary = ...;

    // 項目4の作法に従い、インスタンス化を抑止
    private SpellChecker() {}

    public static boolean isValid(String word) { ... }
}
```

### NG(シングルトンとなるように実装)

```java
// SpellChecker.INSTANCE.isValid("some-word"); のように使う
public class SpellChecker{
    // スペクチェックに使う辞書
    private final Lexicon dictionary = ...;

    // 項目4の作法に従い、インスタンス化を抑止
    private SpellChecker() {}
    public static SpellChecker INSTANCE = new SpellChecker(...);

    public static boolean isValid(String word) { ... }
}
```

これらの NG 例では 1 つの辞書しか使えないため，状況に応じて辞書を切り替えることができない(`setDictionary(lexicon)`のようなメソッドを用意して，後から変更できるようにする手段もあるが，分かりにくくスレッドセーフでもない

そもそも，辞書が状況によって変わるので，インスタンス化して利用されるようなクラスとして実装すべき

### OK(依存性注入のスタイルで実装)

```java
public class SpellChecker{
    // スペクチェックに使う辞書
    private final Lexicon dictionary;

    // 辞書という「状態」を持つのでインスタンス化して利用させる
    // この時に辞書という依存性を注入する
    public SpellChecker(Lexicon dictionary) {
        this.dictionary = Objects.requireNonNull(dictionary);
    }

    public static boolean isValid(String word) { ... }
}
```

## 項目 6 不必要なオブジェクトの生成を避ける

不変なオブジェクト(イミュータブルなオブジェクト)は常に安全に再利用できるため，イミュータブルであるという性質はとても重要

### NG その 1

```java
// new String()で、不要なオブジェクトを生成している。
// "bikini"で、不要なオブジェクトを生成している。
String s = new String("bikini");
```

### OK

```java
// 生成されるオブジェクトは、"bikini"のStringインスタンスのみ。
// 同じJVM内であれば、文字列リテラル"bikini"のインスタンスは常に再利用される。
String s = "bikini";
```

### NG その 2

```java
// コンストラクタなので、常に新たなオブジェクトが生成されてしまう。
new Boolean(String);
```

### OK

```java
// staticファクトリメソッドでは、新たなオブジェクトを生成する必要はない。
// trueあるいはfalseのBooleanオブジェクトが、再利用される。
Boolean.valueOf(String);
```

### NG その 3

```java
// matchesの内部でPatternオブジェクトが生成される。
// isRomanNumeral()が呼び出されるたび、Patternオブジェクトが生成されてしまう。
static boolean isRomanNumeral(String s){
    return s.matches("正規表現。内容は省略します。");
}
```

### OK

```java
public class RomanNumerals {
    // Patternオブジェクトを再利用している。
    private static final Pattern ROMAN = Pattern.compile("正規表現。内容は省略します。");

    static boolean isRomanNumeral(String s) {
        return ROMAN.matcher(s).matches();
    }
}
```

### NG その 4

```java
// オートボクシングでのNG例
private static long sum() {
    Long sum = 0L;
    for (long i = 0; i <= Integer.MAX_VALUE; i++)
        // Longはイミュータブルなので、加算の度に新たなインスタンスが生成されてしまう。
        sum += i;

    return sum;
}
```

### OK

```java
private static long sum() {
    // プリミティブ型に変更（Long -> long）
    long sum = 0L;
    for (long i = 0; i <= Integer.MAX_VALUE; i++)
        sum += i;

    return sum;
}
```
