# 表面上の改善

## 名前に情報を詰め込む

- 明確で正確な単語を選ぶ
    - 例えば`get`ではなく`fetch`や`download`など
- 汎用的な名前を避ける
    - 変数の値を表す名前など
    - あるいは使う状況を選ぶ(`tmp`など)
- 抽象的な名前よりも具体的な名前を使って物事を詳細に説明する
- 接尾辞や接頭辞を使って情報を追加する
    - 値の単位や重要な属性などを`_`を使って区切るなど
- 名前の長さを決める
    - スコープが広いなら長い方が良い
    - 省略しすぎてわからなくならないように
    - 不要な単語は捨てる
- 名前のフォーマットで情報を伝える
    - クラスのメンバ変数なら`_`を付けるなどして区別する

## 誤解されない名前

- `filter()`→選択するなら`select()`，除外するなら`exclude()`など
- 上限の限界値を決めるとき : `max_`や`min_`をつける
- 包含的範囲 : `first`や`last`を使う
- 包含・排他的(最後を含まない)範囲 : `begin`や`end`を使う
- ブール値に名前を付けるとき : `is`や`has`などを使う・否定形は避ける
- 単語に対するユーザの期待に注意する
    - `get()`や`size()`には軽量なメソッドが期待される

## 美しさ

- 複数のコードブロックで同じようなことをしていたら，シルエットも同じようなものにする
    - 似ているコードは似ているように見せる
- コードの「列」を整列すれば，概要が把握しやすくなる
    - 改行位置を簡潔で一貫的に
    - メソッドを使うことも有効
    - 重複を排除する
    - 空白でそろえる
        - 引数が複数ある時など
- 意味のある順番を選んで，常にその順番を守る
    - 重要度やアルファベット順など
- 空行を使って大きなブロックを論理的な「段落」に分ける
    - 関連するコードをまとめてブロックにする
        - 宣言や手順など

## コメントすべきことを知る

- コメントすべきではないこと :
    - コードからすぐにわかること
    - ひどいコードを補足する「補助的なコメント」
        - →コメントを書くのではなくコードを修正する
- 記録すべき自分の考え :
    - なぜコードが他のやり方ではなくこうなっているのか
        - 実行するとどうなるかや修正すべきことなども
    - コードの欠陥を示す
        - 「TODO :」あとでやること
        - 「FIXME :」既知の不具合がある
        - 「HACK :」あまりきれいではない解決策
        - 「XXX :」大きな問題がある
    - 定数の値にまつわる「背景」
- 読み手の立場になって考える :
    - コードを読んだ人が疑問に思うところを予想してコメントをつける
    - 平均的な読み手が驚くような動作は書いておく
    - ファイルやクラスには「全体像」のコメントを書く
        - 何をするかなど
    - 読み手が細部にとらわれないように，コードブロックにコメントをつけて概要をまとめる

## コメントは正確で簡潔に

- 複数のものを指す可能性がある指示語などの代名詞を避ける
- 関数の動作はできるだけ正確に説明する(歯切れをよくする)
    - 「～かどうかで…する」ではなく「～したら…する」
    - 「行数を数える」ではなく「\nの数を数える」など
- コメントに含める入出力の実例を慎重に選ぶ(コーナーケースを選ぶ)
- コードの意図は，詳細レベルではなく，高レベルで記述する
- よくわからない引数にはインラインコメントを使う
    - 例えば`Function(/* arg = */ ...)`
- 多くの意味が詰め込まれた言葉や表現を使って，コメントを簡潔に保つ
    - 例 : 「正規化」「ヒューリスティック」など

# ループとロジックの単純化

## 制御フローを読みやすくする

- 比較では変化する値を左に，より安定した値を右に配置する
    - `bytes_received < bytes_expected`のように
- `if/else`分のブロックは適切に並び替える
    - 肯定形・単純・目立つものを先に処理
- 三項演算子は簡潔になる時にのみ使い，なるべく`if`文に代える
- `do/while`ループ・`goto`などは代替を使う
- 深いネストを避けて「直線的」なコードを選択する
    - 失敗ケースは早めに返す
    - ループ内部では`continue`を使うなど
- 関数において早めに返すと，ネストを削除したりコードをクリーンにしたりできる
    - 特に「ガード節」(関数の上部で単純な条件を先に処理するもの)が便利

## 巨大な式を分割する

- 説明変数(式を表す変数)を使う．
    - `line.split(':')[0].strip()=...`の左辺を`username`という変数に代入するなど
    - 簡潔な名前で式を説明することで，コードを文書化できる
    - コードの主要な「概念」を読み手が認識しやすくなる
- 要約変数(大きなコードの塊を小さな名前に置き換えて，管理や把握を簡単にする変数)を使う
    - 条件式を`boolean`型の変数に代入するなど
- ド・モルガンの法則を使って論理式を読みやすくする
- 短絡評価の悪用(複雑なロジックになってしまう)
    - 短絡評価:`if (a || b) ...`のとき`a`が`true`なら`b`は評価されない
- より優雅な手法を見つける
    - 条件の否定を取ってみるなど
- 同じ手法で巨大な文も分割する
- マクロを用いると簡潔で読みやすくなることがある

## 変数と読みやすさ

- 邪魔な変数を削除する
    - 「中間結果」を保持する変数を使わなくても，結果をそのまま使ってタスクを完了できるならそうする
    - 制御フロー変数(プログラムの実行を制御するためだけの変数`done`など)は削除できる→`break`などを使う
- 変数のスコープをできるだけ小さくする
    - 例えばクラス内でグローバル変数をローカル変数に格下げできるならする
    - メソッドをできるだけ`static`にする(メンバ変数とは関係ないことになるから)
    - 大きなクラスを小さなクラスに分割する
- 変数は一度だけ書き込む
    - できるだけ変数の変更箇所は少ない方が良い
    - あるいは`const`や`final`などでイミュータブルにするなど

# コードの再構成

## 無関係の下位問題を抽出する

- 関数やコードブロックを見て「このコードの高レベルの目標は何か？」と自問する
- コードの各行に対して「高レベルの目標に直接的に効果があるのか？あるいは，無関係の下位問題を解決しているのか？」と自問する
- 無関係の下位問題を解決しているコードが相当量あれば，それらを抽出して別の関数にする
	- 完全に独立していなくても効果はある
- 純粋なユーティリティコードや汎用コードなど
	- コードが独立していると改善が楽になる
- 理想とは程遠いインターフェースに妥協することはない

## 一度に 1 つのことを

- コードは 1 つずつタスクを行うようにしなければいけない
- タスクは小さくできる
	- 異なる関数(あるいは少なくとも領域)に分割する
- オブジェクトから値を抽出する

## コードに思いを込める

- コードの動作(ロジックを)簡単な言葉で明確に説明する
- ライブラリが何を提供してくれるかを知ると簡潔にコードを書くことができる
- 手法を再帰的に適用する

### 短いコードを書く

- 不必要な機能をプロダクトから削除する．過剰な機能は持たせない
- 質問と要求の分割
	- 最も簡単に問題を解決できるような要求を考える
- コードを小さく保つ
	- 汎用的な「ユーティリティ」コードを作って，重複コードを削除する
	- 未使用のコードや無用の機能を削除する
	- プロジェクトをサブプロジェクトに分割する
	- コードの「重量」を意識する．軽量で機敏にしておく
- 定期的にすべての API を読んで，身近なライブラリに親しむ

# 選抜テーマ

## テストと読みやすさ
- テストを読みやすくして保守しやすいものにする
	- 一般的な設計原則として，大切ではない詳細はユーザから隠し，大切な詳細は目立つようにする
	- 入出力のテストはコード1行で記述できるといい
- エラーメッセージをバグの発見や修正がしやすいように読みやすくする
- テストに有効な最も単純な入力値を使う
- テスト関数に説明的な名前を付けて，何をテストしているのかを明らかにする
